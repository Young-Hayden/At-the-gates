## 3. 功能发现（按优先级）

### [P1] AI 进攻波交战后不续走，路径被挡后也不重寻路

- **位置**：`Assets/Scripts/AIController.cs:720-737`、`:764-778`；对照 `Assets/Scripts/CombatAI.cs:278-286`。
- **根因**：`LaunchAttack → SendTo` 只调用 `mover.SetPath(path)`，没有给 `CombatAI` 下 `AttackMove` 命令。因此 `CombatAI` 仍是 `Auto`，没有目标格可在交战结束后恢复；`UnitMover` 因新建筑阻断而 `Stop()` 后，也没有所属命令负责重新寻路。
- **触发 A**：AI 单位在前往攻击目标途中打死一个守军。
- **触发 B**：AI 单位行进途中，前方路径格被新建筑占用。
- **表现 vs 期望**：单位在原地进入普通自动索敌；期望是消灭路上敌人后继续攻击波目标，或绕开新障碍。
- **证据（已复现）**：
  - 交战复现：守军死亡后 2 s，攻击者距波次目标仍有 **8.83 格**，`Moving=False`、`Target=null`。
  - 阻挡复现：在 `(4,0)` 加阻挡后，单位停在 `(3.5,0.5)`，距目标 **7 格**，`Moving=False`、`Target=null`。
- **最小修法**：`SendTo` 在路径存在时，若单位有 `CombatAI`，先 `OrderAttackMove(dest.Value)`，再 `mover.SetPath(path, ai.CompleteOrder)`；无 `CombatAI` 才退回原路径逻辑。不要另写一套 AI 追击状态机。
- **回归测试**：① 杀死后继续到原目标；② 新建筑挡住旧路后绕路到原目标；③ 不可达时退出命令且可继续普通自动索敌。

### [P1] 普通送货途中卸货点被毁，货物仍在旧终点入账

- **位置**：`Assets/Scripts/Gatherer.cs:632-687`，尤其 `:643-655` 与 `OnReachedDropoff`。
- **根因**：`StepToDropoff` 发现目标失效后只把 `dropoff=null`，没有 `mover.Stop()`；若仍在移动就直接返回，旧路径和旧到达回调继续生效。`OnReachedDropoff` 也没有像撤退路径那样重新校验目标是否仍为可用卸货点。
- **触发**：工人背满资源前往基地，途中基地被摧毁且没有其他卸货点。
- **表现 vs 期望**：实测工人在旧基地位置卸货，资源进入银行；期望是保留货物并等待/寻找新卸货点。撤退路径 `OnReachedRetreatBase` 已明确采用后者，普通路径与之不一致。
- **证据（已复现）**：唯一卸货点销毁后 `dropoffsAlive=0`；随后 `carrying 5→0`、`wood 0→5`，工人位置 `(5.5,0.5)`。
- **最小修法**：目标失效时同时停止旧移动；到达回调先验证 `dropoff` 存活、完工、仍为卸货点，失败则保留 `carrying`、清目标并留在 `ToDropoff`。可复用撤退路径的失效判断口径。
- **回归测试**：普通（非撤退）送货途中销毁唯一基地，等待超过旧路径全长，货物与银行都必须不变；随后建立替代基地，只入账一次。

### [P2] 直接内存 API 的 null 容器会中断恢复并留下 0 倍速（修复阶段已更正范围）

- **位置**：`Assets/Scripts/SaveGameService.cs:294-329`（校验）、`:339-506`（恢复），尤其 `:348-349`、`:369`、`:504`。
- **根因**：`Validate` 对 buildings/units/bushes 的 `foreach` 允许 null；`RestoreSnapshot` 随后直接读 `data.buildings.Count`。同时 `Time.timeScale=0` 没有 `try/finally` 保护。
- **触发**：调用方直接构造 `SaveGameData` 并把列表字段设为 null。修复阶段进一步证实：`JsonUtility.FromJson` 会把 JSON null 列表归一化为空数组，因此**普通损坏 JSON 文件不会沿此路径传入 null**，原先关于文件路径的推断撤回。
- **表现 vs 期望**：`NullReferenceException`，完成回调不执行，`Time.timeScale` 留为 0；期望是读档前拒绝并显示错误，至少不能冻结整个对局。
- **证据（已复现）**：`threw=True`、`callback=False`、`timeScale=0`。
- **最小修法**：`Validate` 显式拒绝所有必需的 null 容器；恢复中设置 0 倍速的区段加 `try/finally`，确保恢复原倍速。UI 应把失败原因显示出来，而不只 `Debug.LogError`。
- **回归测试**：分别对 buildings/units/ai/bushes 为 null 做参数化测试；要求不抛异常、有明确错误、时间缩放恢复、原场景不被半毁。

### [P1] 存档替换存在“旧档已删、新档未就位”的丢失窗口

- **位置**：`Assets/Scripts/SaveGameService.cs:55-75`，关键为 `:64-66`。
- **根因**：写临时文件后执行 `File.Delete(path)`，再 `File.Move(temp,path)`；两步之间崩溃/断电会同时失去旧档和正式新档。
- **表现 vs 期望**：异常中断后可能没有 `save_slot_1.json`；期望是任一时刻至少保留一份可读取旧档或新档。
- **证据（静态推断）**：代码顺序确定；本轮没有为了取证而制造崩溃或断电。
- **最小修法**：Windows/.NET 下使用带备份的 `File.Replace`，或先保留 `.bak` 再替换；启动/读取时在正式档损坏时提供备份恢复。仍保留临时文件完整写入与校验。
- **回归测试**：注入替换失败，断言旧档仍可读取；再验证成功路径只替换一次、备份可回滚。

### [P2] 混合选择右键“敌人 + 资源点”时，资源语义吞掉士兵的显式攻击

- **位置**：`Assets/Scripts/SelectionManager.cs:407-434`；顺序为资源 → 草丛 → 塔 → 敌人 → 维修 → 地面。
- **根因**：只要选中集合里有工人接受采集，`AssignGatherers` 就返回 true，整个 `IssueMove` 返回，士兵收不到这次点击的命令。
- **触发**：框选工人和士兵，右键一个与敌人重叠的资源点；把敌人放在士兵 aggro 范围外可排除自动索敌掩盖。
- **表现 vs 期望**：工人去采集，士兵不动也不以敌人为目标；期望是工人采集、战斗单位攻击，或至少按统一规则获得地面命令。
- **证据（已复现）**：距离约 10.05，`immediateMoving=False`、`immediateTarget=False`，两帧后仍不变，`workerTargetsNode=True`。近距离复测会被自动索敌掩盖，因此不拿近距离结果作证。
- **最小修法**：把“是否处理了点击”和“哪些单位接了命令”分开；资源/维修/清草命令只消费工人部分，再让其余战斗单位执行敌人/地面命令。若产品上刻意规定混合选择只派工人，应写入操作说明并视为设计，而非静默行为。
- **回归测试**：混合选择、敌人在 aggro 外且与资源重叠，断言工人采集且士兵收到攻击；纯工人选择仍只采集。

### [P2] 结算状态下关闭暂停面板会把时间恢复为 1

- **位置**：`Assets/Scripts/UI/PauseMenu.cs:116-128`；相关 `Assets/Scripts/GameState.cs:220-243`。
- **根因**：`SetOpen(false)` 无条件写 `Time.timeScale=1`，而 `GameState.End` 用 0 倍速冻结结算，且没有禁用所有 `UnitMover`/建筑计时器。
- **证据（API 已复现；自然键鼠路径未验证）**：`SetOpen(true) → GameState.End → SetOpen(false)` 后，`IsOver=True`、`timeScale=1`。
- **边界**：正常对局中“暂停面板开着且恰好结算”的可达路径较窄，本项不冒充已观察到的真人操作流程。
- **最小修法**：关闭面板时若 `GameState.IsOver`，保持 0；否则恢复 1。
- **回归测试**：结算状态调用关闭面板仍保持 0；普通开关仍保持现有 1→0→1 行为。

## 7. 性能实测与优化顺序

### 7.1 测量环境与限制

- 数据来自本机编辑器 PlayMode，不是独立播放器；1920×1080，性能对照阶段 `timeScale=1`。
- 帧时间使用 `Time.unscaledDeltaTime`；GC 使用 `ProfilerRecorder("GC Allocated In Frame")`；函数成本用 `Stopwatch` 重复调用。
- 600 s 长局使用 `timeScale=5`，只用于稳定性/漂移观察，不与正常速度帧时间混算。

### 7.4 按性价比排序的改法

#### [优化 1 · 现在就该做] 停止每帧重建人口/兵种名簿

- **现状证据**：完整 HUD 约 154 KB/帧；仅人口或商店刷新就约 153 KB/帧；关闭后约 7.7 KB/帧。
- **瓶颈**：`UnitLimits.Counts` 虽按 `Time.frameCount` 缓存，但 HUD 每帧都查询，所以仍然每帧重建字典、遍历单位/建筑并 `FindObjectsByType<ProductionBuilding>`。位置：`UnitLimits.cs:142-192`；入口 `HUD.cs:544-618`、`:857-870`。
- **具体改法**：最短路径是让人口与商店刷新以 10 Hz 左右更新，点击下单时立即强制刷新一次。更彻底的路径是把名簿缓存改为 dirty/变更驱动，并在单位出生、死亡、驻塔/出塔、队列变化时统一 `Invalidate`；不能只删 frame cache 而不补死亡/驻塔失效点。
- **预期收益与规模**：本轮机器上，HUD 查询停止时少约 145 KB/帧分配；帧时间对照约 0.7–1.0 ms。当前规模就值得做。
- **风险/回归**：按钮可用状态、人口读数、排队数量不能陈旧；覆盖出生、死亡、驻塔、取消、读档和同帧多次下单。保留现有 Population/UnitLimit/HUD 测试并新增同帧死亡刷新测试。

#### [优化 2 · 现在就该做] AI 选址共享一次单位占格快照

- **现状证据**：一次 `FindSite` 17.8–20.0 ms；每候选带单位检查 0.159 ms，不带为 0.014 ms。
- **瓶颈**：`AIController.Fits → PlacementRules.ValidateCells(checkUnits:true)` 在每个候选位置调用 `FindObjectsByType<UnitMover>`。位置：`AIController.cs:312-387`，`PlacementRules.cs:31-39`。
- **具体改法**：在 `FindSite` 开始时构造一次单位占格 `HashSet`，候选检查共享它；保持地形、坡度、草丛、间距规则不变。玩家的低频放置校验无需改写。
- **预期收益与规模**：消除随候选数增长的全场景扫描；实测单候选差约 0.145 ms，是当前 20 ms 尖峰的主要部分。具体修后总毫秒必须复测，不预先写死。
- **风险/回归**：首选格有单位时必须继续找下一格；同一 tick 内移动单位以快照为准，提交前可再校验一次。新增“最近候选被单位占用则选择下一可达位置”测试，并复跑 Placement/AIProduction。

#### [优化 3 · 现在可做] 小地图降频渲染，视口仍逐帧更新

- **现状证据**：两轮关小地图均约省 0.8–0.9 ms/帧，GC 基本不变，符合额外渲染而非脚本分配。
- **瓶颈**：`Minimap.cs:48-86` 的 900×500 第二相机每帧整图渲染，`cullingMask=-1`。
- **具体改法**：相机不每帧自动渲染，以 5–10 Hz 主动 `Render()`；`UpdateViewport` 继续跟随主相机逐帧，点击跳转逻辑不变。
- **预期收益与规模**：减少第二场景的渲染频率；实际收益随频率和地图规模复测。
- **风险/回归**：动画/单位在小地图上低频跳动是可接受的观感折衷，需用户确认；检查禁用/启用、场景销毁时 RenderTexture 和相机释放不变。

#### [优化 4 · 顺手但非首要] 缓存 Garnish 根对象

- **现状证据**：`IsBushCell` 单次约 0.0061 ms；`GarnishRules.cs:23-46` 即使已有格缓存也每次 `GameObject.Find("Garnish")`。
- **改法**：缓存根对象，仅在其为空/失效或 `Invalidate` 后重新 Find；保留清草与读档后的失效。
- **定位**：在优化 2 之后复测，它不再是最大头；不要把它单独宣传成 20 ms 的完整修复。

#### [规模上去才需要 / 本轮不建议先做]

- **投射物、特效、飘字对象池**：关闭 HUD 后稳态背景 GC 已只有约 8 KB/帧，没有证据表明这些 Instantiate/Destroy 是当前首要瓶颈。
- **A* 重写**：0.704 ms/次需要关注批量同帧追击，但当前战斗上限 14；先错开/复用 AI 命令路径，不必重写寻路。
- **图集/物理矩阵**：938 draw calls 值得后续在独立播放器 profiling，但本轮未拆分图集收益；0 Rigidbody2D 且主要用于点查询，没有依据把碰撞矩阵列为优先项。
- **YSort/Animator 精修**：数量已记录，未做单独 A/B，不给收益数字。
